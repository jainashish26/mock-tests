## 10. Deliverable 10 — Stripe ingestion and reconciliation

### 10.1 What already exists

`public.processed_webhook_events` has a **unique `event_id`** and is written by
`src/app/api/webhooks/stripe/route.ts` with signature verification. `public.purchases` gained
`provider_ref` (unique), `payment_intent` (unique, partial), `stripe_customer_id` and
`product_id` in `010_subscriptions.sql`. **Idempotency on event ID is therefore already in place**
— the design builds on it rather than replacing it.

What is missing for reporting: no fees, no GST split, no dispute table, no refund table with a
period, no subscription period history, and no reconciliation.

### 10.2 Ingestion design

```
Stripe ──webhook──► POST /api/webhooks/stripe
                        │ 1. constructEvent (signature verified)
                        │ 2. INSERT processed_webhook_events(event_id)
                        │    ON CONFLICT DO NOTHING  ← idempotency gate
                        │    if no row inserted: return 200 immediately
                        │ 3. route by event type to a handler
                        ▼
                   public.stripe_events        (raw payload, 90-day retention)
                   public.stripe_charges       (one row per charge, upserted)
                   public.stripe_refunds       (one row per refund)
                   public.stripe_disputes      (one row per dispute)
                   public.stripe_balance_txns  (fees — arrives separately!)
                   public.subscriptions        (010, upserted)
                        │
                        │ nightly ETL (blackout-guarded)
                        ▼
                   reporting.fact_order  /  reporting.fact_subscription
```

**Events subscribed to:** `checkout.session.completed`, `payment_intent.succeeded`,
`payment_intent.payment_failed`, `charge.succeeded`, `charge.refunded`, `charge.dispute.created`,
`charge.dispute.closed`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.created`,
`customer.subscription.updated`, `customer.subscription.deleted`.

### 10.3 The two problems that break naive Stripe reporting

**1. Fees arrive on a different object, at a different time.** A `charge.succeeded` webhook does
not contain the processing fee — the fee is on the **balance transaction**, which can be created
in a later period. A report that sums charges and subtracts an estimated fee percentage will not
reconcile to the Stripe balance. Design: `stripe_balance_txns` is upserted independently, keyed on
`balance_transaction_id`, and `fact_order.fee_cents` is joined late. `mv_revenue_daily` treats
`kind='fee'` as its own row class, so revenue and fees are never conflated.

**2. GST is not a Stripe concept.** Stripe does not compute Australian GST unless Stripe Tax is
configured, and nothing in the repo indicates it is. The `/1.10` in `net_revenue_ex_gst` is
therefore an **assumption that every line is taxable**, stated in the view comment and flagged in
the metric dictionary. If any product is ever GST-free (some educational supplies can be), the
divisor is wrong and revenue is misstated. **Question Q-7.**

### 10.4 Nightly reconciliation

```sql
CREATE TABLE public.stripe_reconciliation (
  recon_id       bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  recon_date     date NOT NULL,
  source         text NOT NULL,          -- 'charge_list' | 'balance_summary' | 'subscription_list'
  stripe_count   integer,
  local_count    integer,
  stripe_cents   bigint,
  local_cents    bigint,
  gap_count      integer NOT NULL DEFAULT 0,
  gap_cents      bigint  NOT NULL DEFAULT 0,
  status         text NOT NULL DEFAULT 'ok',   -- ok | gap | error
  detail         jsonb NOT NULL DEFAULT '{}'::jsonb,
  ran_at         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (recon_date, source)
);
```

The reconciliation job (`/api/cron/stripe-reconcile`, QStash-scheduled, service role) does a
three-way comparison for the previous day:

| Check | Stripe side | Local side | Gap definition |
|---|---|---|---|
| Charges | `GET /v1/charges?created[gte]=…&created[lt]=…`, paginated | `stripe_charges` | Any `id` present in one and not the other, or an amount mismatch |
| Balance | `GET /v1/balance_transactions`, or the balance summary report | `stripe_balance_txns` | Net movement differs |
| Subscriptions | `GET /v1/subscriptions?status=all`, paginated | `subscriptions` | Status or `current_period_end` differs |
| Refunds/disputes | `GET /v1/refunds`, `GET /v1/disputes` | `stripe_refunds`, `stripe_disputes` | Count or amount differs |

Rules:
- **Pagination is mandatory.** A single-page fetch silently under-counts past 100 objects and
  produces a "gap" that is really a bug. `has_more` is followed to exhaustion.
- **The API is the source of truth, not the webhook.** Webhooks can be missed (endpoint down,
  signature rotation, network). Reconciliation exists precisely to catch that.
- **A gap blocks the A8 refresh.** `safe_refresh` checks `stripe_reconciliation.status = 'gap'`
  for the target date and logs `skipped_upstream_gap` rather than publishing revenue that is known
  to be wrong. Publishing a wrong revenue number once destroys trust in every other number.
- **Gaps auto-heal where possible**: a charge present in Stripe and absent locally is inserted from
  the API response. A local row absent from Stripe is *never* deleted automatically — it is flagged
  for a human, because deleting revenue is not a safe automatic action.
- Retention: `stripe_reconciliation` is kept 7 years (financial record).

## 11. Deliverable 11 — AI writing marking quality monitoring

**No human moderation exists.** That makes this the only quality gate between an unvalidated model
output and a parent's belief about their child's writing. It is the highest-stakes monitoring in
the system.

### 11.1 What is missing today

`public.writing_evaluations` has `provider` (default `'DeepSeek'`), `score_out_of100`,
`strengths`, `improvements`, `improved_text`, `raw_response`. There is **no model version, no
rubric version, no status, no timing, no criterion-level breakdown and no flag**. Every metric in
A5/A6/A7 is unbuildable until the source is extended. Additive migration — nothing dropped or
renamed:

```sql
ALTER TABLE public.writing_evaluations
  ADD COLUMN IF NOT EXISTS model_version    text,
  ADD COLUMN IF NOT EXISTS model_name       text,
  ADD COLUMN IF NOT EXISTS rubric_version   text,
  ADD COLUMN IF NOT EXISTS prompt_id        text,
  ADD COLUMN IF NOT EXISTS status           text NOT NULL DEFAULT 'complete'
    CHECK (status IN ('queued','processing','complete','failed','retrying')),
  ADD COLUMN IF NOT EXISTS attempts_to_mark smallint NOT NULL DEFAULT 1,
  ADD COLUMN IF NOT EXISTS queue_ms         integer,
  ADD COLUMN IF NOT EXISTS mark_ms          integer,
  ADD COLUMN IF NOT EXISTS submitted_at     timestamptz,
  ADD COLUMN IF NOT EXISTS marked_at        timestamptz,
  ADD COLUMN IF NOT EXISTS error_class      text,
  ADD COLUMN IF NOT EXISTS word_count       integer,
  ADD COLUMN IF NOT EXISTS criterion_scores jsonb;  -- {criterion:{score,max,feedback}}
-- Existing rows keep NULL versions and are EXCLUDED from drift metrics, reported
-- as model_version = 'UNKNOWN' rather than silently averaged in.
```

### 11.2 Anchor set (A5)

```sql
CREATE TABLE public.marking_anchor_set (
  anchor_id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  script_text      text NOT NULL,             -- the reference script
  prompt_id        text NOT NULL,
  year_level       smallint NOT NULL,
  agreed_score     numeric(5,2) NOT NULL,     -- HUMAN-AGREED, frozen before any run
  criterion_agreed jsonb NOT NULL,            -- per-criterion agreed scores
  agreed_by        uuid NOT NULL REFERENCES auth.users(id),
  agreed_at        timestamptz NOT NULL,
  rubric_version   text NOT NULL,
  is_active        boolean NOT NULL DEFAULT true,
  locked_at        timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE public.marking_anchor_runs (
  run_id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  anchor_id      uuid NOT NULL REFERENCES public.marking_anchor_set(anchor_id),
  model_name     text NOT NULL,
  model_version  text NOT NULL,
  rubric_version text NOT NULL,
  ai_score       numeric(5,2) NOT NULL,
  ai_criteria    jsonb NOT NULL,
  ran_at         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (anchor_id, model_version, rubric_version, ran_at)
);
```

**The critical rule: anchors are scored by a human and frozen *before* the model runs.** If an
anchor's agreed score is revised after seeing AI output, `anchor_agreement` measures nothing.
`locked_at` and the absence of any UPDATE path in the API enforce this.

Schedule: the anchor set is re-marked **weekly** and **on every model or rubric version change**,
detected from the version string the marking job records. Re-marking on version change is what
catches a silent upstream model update — the most likely failure mode with a hosted LLM, because
the provider can change behaviour without you deploying anything.

`anchor_agreement` is reported two ways, because a mean alone hides the failure that matters:
- **Mean absolute error** against the agreed score.
- **Adjacent-band agreement** — the proportion of anchors where the AI band equals, or is one band
  from, the agreed band. A marker that is never wildly wrong but always one band out is unusable,
  and MAE alone can make that look acceptable.

### 11.3 Consistency (A5)

A **random sample** of live scripts is re-marked *n* times (default 3) with the same model and
rubric version, and the spread recorded. Random, not chosen — re-marking the easiest scripts
overstates stability.

```sql
CREATE TABLE public.marking_remarks (
  remark_id      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  evaluation_id  uuid NOT NULL REFERENCES public.writing_evaluations(id),
  run_ordinal    smallint NOT NULL,
  model_version  text NOT NULL,
  rubric_version text NOT NULL,
  score          numeric(5,2) NOT NULL,
  criteria       jsonb NOT NULL,
  ran_at         timestamptz NOT NULL DEFAULT now(),
  UNIQUE (evaluation_id, run_ordinal, model_version)
);
```

The sample size is stored alongside the result so `remark_score_stability` is never read without
its n.

### 11.4 Fairness and bias (A6)

| Check | Metric | Interpretation |
|---|---|---|
| **Length bias** | `CORR(word_count, score)` by prompt × year level × model version | A strong positive correlation means verbosity is rewarded. Reported **with n** — on 12 scripts a correlation proves nothing. |
| **Distribution drift** | Mean and deciles vs a **frozen baseline period** | "Drift" is undefined without a baseline. The baseline is frozen once `[config]` marks exist; re-freezing is an audited action. |
| **Year-level drift** | Same, partitioned by year level | A model can be stable overall while drifting badly at one year level, and the aggregate hides it. |
| **Version drift** | Same, partitioned by `model_version` | Separates a version change from a genuine change in student writing. |

I am **not** specifying a numeric bias threshold. There is no validated benchmark for acceptable
length correlation in automated writing assessment that I can cite without inventing one. The
threshold is `[config]`, seeded `NULL`, and must be set from observed platform data once a baseline
exists (assumption **A-17**).

### 11.5 Operations and flagging (A7)

`mark_queue_time_p95`, `mark_failure_rate` and `mark_retry_rate` come from the new `status`,
`queue_ms` and `attempts_to_mark` columns plus `WRITING_MARK_COMPLETED`. Retry rate is the earlier
warning — it rises before failure rate does.

`mark_flag_rate` comes from `marking_flags`, **split by `flagged_by_role`**. A tutor flag is a
professional judgement that the mark is wrong; a parent flag is often surprise at a low mark.
Summing them produces a number nobody can act on.

```sql
CREATE TABLE public.marking_flags (
  flag_id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  evaluation_id   uuid NOT NULL REFERENCES public.writing_evaluations(id) ON DELETE CASCADE,
  flagged_by      uuid NOT NULL REFERENCES auth.users(id),
  flagged_by_role text NOT NULL CHECK (flagged_by_role IN ('PARENT','TUTOR','ADMIN')),
  reason_code     text NOT NULL,
  reason_text     text,
  flagged_at      timestamptz NOT NULL DEFAULT now(),
  review_status   text NOT NULL DEFAULT 'open'
    CHECK (review_status IN ('open','investigating','upheld','adjusted','rejected')),
  reviewed_by     uuid REFERENCES auth.users(id),
  reviewed_at     timestamptz,
  UNIQUE (evaluation_id, flagged_by)     -- one flag per person per mark
);
```

Admin review outcomes feed back into A5: a mark `adjusted` on review is evidence the anchor set or
the prompt needs work, and the count of adjustments is the most honest accuracy signal available.

### 11.6 Version recording on every mark

The brief requires model and rubric version on every mark. Enforcement is threefold:
1. `fact_writing_mark.model_version` and `rubric_version` are `NOT NULL` (default `'UNKNOWN'`).
2. `/api/jobs/writing-eval` must pass both, read from config — **never hardcoded in a prompt
   string**, which is how recorded versions drift from reality.
3. A15 counts marks with `model_version = 'UNKNOWN'` written after the migration date. Any is an
   alert, because an unversioned mark can be neither audited nor compared.

## 12. Deliverable 12 — Node.js API specification

### 12.1 Shared contract

All reporting endpoints live under `/api/reporting/<role>/<report-id>`, are Next.js route handlers
(matching the existing `src/app/api/**/route.ts` convention) and share one envelope so no client
has to special-case an error shape.

```typescript
// src/lib/reporting/envelope.ts
export interface ReportEnvelope<T> {
  reportId: string                 // stable ID from 11-…md §4, e.g. 'P1'
  data: T | null                   // null in every non-ok state
  meta: {
    asAt: string                   // ISO: the MV's data timestamp, NOT the request time
    refreshLagMinutes: number      // shown on every dashboard
    cohort?: { size: number; windowMonths: number; definition: 'platform cohort' }
    suppressed?: boolean
    state: 'ok' | 'empty' | 'low_data' | 'error'
  }
  pagination?: { page: number; pageSize: number; totalItems: number; hasMore: boolean }
}
```

**Every response carries `refreshLagMinutes`.** A stale materialised view is indistinguishable from
a correct one; the lag badge is the only defence against acting on yesterday's number as today's.

| Concern | Rule |
|---|---|
| Auth | `requireRole([...])` from the existing `src/lib/rbac/require-role` — reused, not reimplemented |
| DB access | Always through `withReportingRole()` (`SET LOCAL ROLE reporting_ro` + 5s timeout) |
| Authorisation | Enforced by RLS **and** by the route's role check. Neither alone is sufficient. |
| Caching | `Cache-Control: private, max-age=<ttl>, stale-while-revalidate=<ttl*4>`. Never `public` — payloads are per-family. |
| Pagination | Cursor for row-level tables (`?cursor=`), page for aggregates. Caps below. |
| CSV export | `?format=csv` on every admin and tutor table endpoint. Streams; never buffers the full set. |
| Errors | `400` bad filter · `403` not authorised / not linked · `404` no such student · `429` rate limited · `503` upstream stale. Never `500` with a stack trace. |

**Pagination caps** — what keeps the 30 KB payload budget real:

| Endpoint class | Default page size | Hard max |
|---|---|---|
| Student | n/a (single object) | — |
| Parent per-child | 20 | 50 |
| Tutor per-student list | 25 | 100 |
| Admin row-level drill-down | 50 | 500 |
| Admin aggregate | not paginated | capped by date range (max 366 days) |

### 12.3 Two worked examples

**S3 — the completion endpoint. There is no query to get wrong:**

```typescript
// src/app/api/reporting/student/completion/route.ts
import { requireRole } from '@/lib/rbac/require-role'

/**
 * Post-test screen. Returns a constant.
 *
 * There is deliberately NO database read in this handler. A query that cannot run
 * cannot leak. The student role additionally has no column grant on any score
 * field (migration 015), so even a regression here returns nothing sensitive.
 */
const PAYLOAD = {
  reportId: 'S3',
  data: { status: 'completed' as const, message: 'Nice work — you finished!' },
  meta: { asAt: new Date().toISOString(), refreshLagMinutes: 0, state: 'ok' as const },
}

export async function GET() {
  await requireRole(['STUDENT'])
  return Response.json(PAYLOAD, { headers: { 'Cache-Control': 'no-store' } })
}
```

**P2 — B1 enforced in code, not in the UI:**

```typescript
// src/app/api/reporting/parent/percentile/route.ts
export async function GET(req: Request) {
  const studentId = new URL(req.url).searchParams.get('studentId')
  if (!studentId) return badRequest('studentId is required')
  await requireRole(['PARENT'])

  return withReportingRole(async (sql) => {
    // B1: a percentile may never resolve without the personal-progress figure that
    // must be displayed beside it. Enforced here so a future UI change cannot
    // silently drop the pairing.
    const [row] = await sql`
      SELECT p.percentile_rank, p.percentile_band, p.cohort_size, p.suppressed,
             p.cohort_window_months, p.cohort_definition,
             h.personal_progress_delta
      FROM reporting.mv_percentile_cohort p
      JOIN reporting.dim_student ds ON ds.student_key = p.student_key AND ds.is_current
      LEFT JOIN reporting.mv_attempt_history h ON h.student_key = p.student_key
      WHERE ds.student_id = ${studentId}
        AND reporting.can_parent_see(p.student_key)`
    if (!row) return notFound()

    const lowData = row.cohort_size >= 20 && row.cohort_size < 50
    return json<ReportEnvelope<PercentileDto>>({
      reportId: 'P2',
      data: row.suppressed ? null : {
        percentileRank:        lowData ? null : row.percentile_rank,  // band under 50
        percentileBand:        lowData ? row.percentile_band : null,
        personalProgressDelta: row.personal_progress_delta,           // REQUIRED companion
      },
      meta: {
        asAt: row.as_at,
        refreshLagMinutes: row.lag_minutes,
        cohort: { size: row.cohort_size, windowMonths: row.cohort_window_months,
                  definition: row.cohort_definition },
        suppressed: row.suppressed,
        state: row.suppressed || lowData ? 'low_data' : 'ok',
      },
    }, { headers: cacheControl(900) })
  })
}
```

## 13. Deliverable 13 — Wireframe descriptions

**Shared rules.** Every dashboard has four states — **empty** (no data yet, plus the action that
creates data), **low-data** (data exists but is below a threshold; says so and shows what is
available), **error** (what failed, whether it is our fault, what to do), and **ok**. Every
dashboard shows `refreshLagMinutes`. Colour-blind safe throughout: ECharts `aria.decal.show: true`,
so every series also carries a pattern; no state is conveyed by hue alone; every chart has a
`<details>` data table as its accessible equivalent.

### 13.1 Student (mobile-first, no charts, Year 4 reading level)

Single column, one card per concept, bottom nav with two items. No tabs, no drill-down, no
scroll-dependent content.

| Card | Content | Chart |
|---|---|---|
| **S1 Countdown** | Exam name, then one very large number and the word "days". Icon + text. After the exam: "Your exam is done." | None |
| **S2 Today** | "Today's practice", one large number, the unit word, one **Start** button. A CSS progress ring fills as units complete — no red, no failure state, no streak counter. | CSS ring, not a chart |
| **S3 Done** | "Nice work — you finished!" and a **Back to dashboard** button. Nothing else. | None |

**States.** Empty: no exam assigned → "Ask a grown-up to set your exam date." Low-data: cap unset →
target derived from the weekly goal, same presentation, no warning. Error: "We couldn't load your
practice. Try again in a minute." — no technical detail, no retry loop.

**Prohibited on this surface** (B2, B4, B5, B6, B8): any score, percentage, percentile, band, rank,
correct/incorrect indicator, comparison, streak, sub-day countdown timer, red or amber warning
treatment, or any reference to another child.

**States (all parent screens).** Empty: "No practice yet — the first test unlocks this report", with

yet" (P3, <3 items). Error: "We couldn't load this report. Your child's data is safe. Try again." —
never a stack trace, never an implication that data was lost.

### 13.3 Tutor (desktop-first, responsive to tablet; dense but scannable)

**States.** Empty: "No students linked yet. A parent must grant access first." — with a link to the
consent explainer, because a tutor facing an empty dashboard otherwise assumes the product is
broken. Low-data: a heatmap cell with <3 items renders as hatched "not enough data" rather than a
mastery level. Error: names the failing report and offers a retry, without exposing SQL.

### 13.4 Admin (desktop, dense, summary → drill-down → row level, CSV everywhere)

Every admin report uses the same three-level structure: **KPI strip** (5–8 numbers with
period-over-period deltas and sparklines) → **primary chart** → **row-level table**. Row-level
student data is reachable **only** through the audited drill-down modal, which requires a task
reason before returning anything.

| Report | Primary chart | Justification |
|---|---|---|
| **A1** Item statistics | **Scatter**: p-value (x) vs point-biserial (y), point size = n, flagged items marked by shape as well as colour | "Which items are defective" is a two-variable outlier problem. A scatter shows the defective quadrant directly; a table needs two sorts for the same insight. Shape encoding keeps it colour-blind safe. |
| **A2** Adaptive engine health | **Line** of exposure rate over time + **stacked bar** of pathway distribution | Drift is a time-series question; pathway mix is a composition question. Two charts because they are two questions. |
| **A3** Curriculum coverage | **Horizontal stacked bar** per level: adequate / too few / all-too-easy / all-too-hard / none | Composition per category with long labels. Stacking shows both the total item count and its balance. |
| **A4** Test-level metrics | **Histogram** of score distribution + start→submit **funnel** per form | Distribution *shape* is the question (bimodal, ceiling, floor). A histogram is the only chart that shows shape. |
| **A5** Marking accuracy | **Line** of anchor agreement per run, with version changes as annotated vertical markers | Drift over time with causation annotated. Without the markers a drift is unexplained. |
| **A6** Marking bias | **Scatter** of word count vs score with a fitted line and r displayed, faceted by year level | A correlation question. Faceting stops an aggregate from hiding a single-level problem. |
| **A7** Marking ops | **Line** of p95 queue time + **bar** of failure/retry rates | Latency is a time series; rates are counts per period. |
| **A8** Revenue | **Stacked bar** by kind (charge / refund / dispute / fee) + KPI strip | Stacked so refunds and disputes stay visible instead of being netted away — netting hides the exact problem this report exists to surface. |
| **A9** Revenue by offering | **Horizontal bar**, sorted, with a table beneath | A ranking question. Sorted bars; the table carries exact figures. |
| **A10** Cohort retention & LTV | **Retention triangle heatmap** + **line** of LTV-to-date by cohort month | Cohort retention is conventionally a triangle and is the one format practitioners read correctly. LTV-to-date is a time series. |
| **A11** Conversion funnel | **Funnel** with absolute counts *and* percentages on every step, plus a segment filter row | Counts beside rates is unambiguous and prevents the "50% drop on 2 users" misreading. |
| **A12** Experiments | **Forest plot** of the difference with confidence intervals | The decision is "is the interval clear of zero, and is the effect big enough". A forest plot answers both; a two-bar chart answers neither. |
| **A13** Enquiries | **Stacked bar** by channel and type + **line** of first-response minutes against a drawn SLA line | Volume is composition over time; SLA is a threshold crossing, which needs a reference line rather than a second series. |
| **A14** Platform health | **Line** of concurrency with the 200 cap drawn as a reference line + **bar** of errors by hour | The cap is a threshold, so it belongs on the chart, not beside it. |
| **A15** Data quality | **Status table**: check, value, threshold, pass/fail with icon **and** label, last run | A pass/fail list. A chart would obscure which specific check failed. |

**States.** Empty: "No data in this period" plus a date-range widening suggestion — an admin facing
an empty chart otherwise suspects the pipeline. Low-data: any segment below the volume floor is
shown greyed with its n, never suppressed silently, so an admin can distinguish "small" from
"broken". Error: names the failing MV and shows its last successful refresh from
`reporting.refresh_log`.

## 14. Deliverable 14 — Alerting rules

Rules live in `reporting.alert_rules` as **data**, not code, so thresholds can be tuned without a
deploy and the whole alerting policy is reviewable in one query. Every rule states its window,
severity, channel and — critically — its **suppression**, because an alert that fires during a
known-empty pre-launch period gets muted and then ignored when it matters.

| **AL-34** | Access control | Any successful read of `enquiry_contacts` | on write | Low | Daily digest. Expected activity, reviewed weekly — the log exists so the *pattern* is visible |
| **AL-35** | Access control | Any `permission denied` on `reporting.*` for a `STUDENT`-role JWT | hourly | **Critical** | Immediate + paging — an attempted or actual breach of the hard constraint (§15.3) |

**Design notes.**

- **Five alerts are `Critical` + paging**: AL-07/AL-08 (marking accuracy), AL-22 (revenue
  reconciliation), AL-30/AL-31 (capacity and lost submissions), AL-35 (student access breach). More
  than a handful of paging alerts gets muted, so the bar is "a human must act tonight".
- **AL-35 is what makes the access rule operational.** It fires on a *denied* read, so it detects
  probing as well as regression. A rule that fired only on success would detect nothing until after
  a leak.
- **Five alerts are suppressed pre-launch** (AL-06, AL-10, AL-11, AL-21, AL-24) because their
  preconditions do not exist. Each suppression records the condition that lifts it, so a suppressed
  alert cannot be forgotten permanently.
- **Nothing in this table notifies a parent or a student.** AL-16/17/18 go to the *tutor* only. A
  "your child is at risk" push to a parent is precisely the anxiety trigger and dark pattern the
  Behavioural Economist prohibits (B5, B9). The only parent-facing notice anywhere in the system is
  the commercially neutral plan-adjustment message from `plan_overload_flag` (X-5).
