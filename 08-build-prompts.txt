PROMPT 5: RLS Helper Functions
--------------------------------------------------------------------------------

Create a Supabase migration file at `supabase/migrations/002_rls_functions.sql` that defines ALL the RLS helper functions documented in `02-mock-tests-rls-and-seed-plan.md` Section 3.

Create these functions in the `public` schema with `SECURITY DEFINER` and `STABLE` attributes:

1. `has_role(target_role user_role)` → returns boolean
   - Returns true if current user (`auth.uid()`) has the specified role in `app_user_roles`.

2. `is_parent_of(p_student_id uuid)` → returns boolean
   - Returns true if `(auth.uid(), p_student_id)` exists in `parent_student_links`.

3. `is_student_self(p_student_id uuid)` → returns boolean
   - Returns true if a `student_profiles` row exists where `id = p_student_id` AND `auth_user_id = auth.uid()`.

4. `is_attempt_owner(p_attempt_id uuid)` → returns boolean
   - Joins `attempts` → `student_profiles` and returns true if `student_profiles.auth_user_id = auth.uid()`.

5. `has_entitlement(p_test_id uuid)` → returns boolean
   - Returns true if `entitlements` has a row with `user_id = auth.uid()`, `test_id = p_test_id`, and `active = true`.

6. `can_access_published_test(p_test_id uuid)` → returns boolean
   - Returns true if:
     - `auth.uid()` IS NOT NULL (user is logged in), AND
     - The test exists with `status = 'PUBLISHED'`, AND
     - (`is_free = true` OR `has_entitlement(p_test_id)` returns true)

Each function should:
- Set `search_path = public` for security.
- Use `auth.uid()` to identify the caller.
- Be marked as `STABLE` (no side effects).
- Include a brief SQL comment explaining its purpose.

Reference: `02-mock-tests-rls-and-seed-plan.md` Section 3 for exact semantics.

PROMPT 6: RLS Policies
--------------------------------------------------------------------------------

Create a Supabase migration file at `supabase/migrations/003_rls_policies.sql` that enables RLS and defines ALL policies based on `02-mock-tests-rls-and-seed-plan.md` Section 4.

First, enable RLS (ALTER TABLE ... ENABLE ROW LEVEL SECURITY) on ALL these tables:
app_user_roles, student_profiles, parent_student_links, tests, test_sections, questions, test_questions, assignments, attempts, responses, writing_evaluations, notifications, products, product_tests, purchases, purchase_items, entitlements, processed_webhook_events, processed_jobs

Then create policies for each table. Use the helper functions from the previous migration. Policy naming convention: `{table}_{operation}_{who}` (e.g., `tests_select_published_access`).

Follow the COMPLETE policy catalogue from `02-mock-tests-rls-and-seed-plan.md` Section 4 (subsections 4.1 through 4.15). Key rules:

- **app_user_roles**: user reads own; admin reads/writes all.
- **student_profiles**: parent reads linked; student reads self; admin reads all. Parent inserts (child creation). Parent/admin updates.
- **parent_student_links**: parent manages own links; admin manages all.
- **tests (published)**: only `can_access_published_test(id)`.
- **tests (draft/pending)**: creator reads own; admin reads all. Creator inserts drafts. Creator updates own draft/pending. Admin updates any.
- **test_sections**: follows test visibility rules.
- **questions (published)**: logged-in AND question belongs to at least one accessible published test (via test_questions + can_access_published_test).
- **questions (draft/pending)**: creator reads own; admin reads all.
- **test_questions**: follows test visibility rules.
- **assignments**: parent reads for linked students; student reads own; admin all. Parent inserts for linked students.
- **attempts**: student reads/creates/updates own; parent reads for linked students; admin all.
- **responses**: student manages own (via attempt ownership); parent reads via attempt ownership; admin all.
- **writing_evaluations**: read follows attempt access rules; write is service-role only.
- **notifications**: user reads/updates own; admin reads all. Insert via service-role.
- **products, product_tests**: all logged-in users can read; admin writes.
- **purchases, purchase_items, entitlements**: user reads own; admin reads all. Writes via service-role.
- **processed_webhook_events, processed_jobs**: no policies for regular users (service-role only).

IMPORTANT: For the deny-by-default pattern, since RLS is enabled with no policies, access is already denied. Only add ALLOW policies. Never add overly broad policies.

Reference: `02-mock-tests-rls-and-seed-plan.md` Section 4 for the complete policy catalogue, `07-implementation-plan.md` Section 14 for security checklist.

2. Create `src/lib/utils/api-response.ts`:
   - Helper `successResponse(data, status = 200)` — returns NextResponse with JSON body.
   - Helper `errorResponse(code, message, correlationId, status)` — returns NextResponse with shape:
     ```json
     { "error": { "code": "UNAUTHORIZED", "message": "...", "correlationId": "..." } }
     ```
   - Predefined error creators:
     - `unauthorizedError(correlationId)` — 401
     - `forbiddenError(correlationId)` — 403
     - `notFoundError(correlationId)` — 404
     - `validationError(message, correlationId)` — 400
     - `rateLimitError(correlationId)` — 429
     - `serverError(correlationId)` — 500

3. Create `src/lib/rbac/guards.ts`:
   - `getUserRole(userId: string)` — queries `app_user_roles` table, returns the role string or null.
   - `requireAuth(request)` — async function that:
     - Creates a Supabase server client.
     - Gets the session user.
     - If no user, returns an unauthorizedError.
     - Returns the user object.
   - `requireRole(request, allowedRoles: string[])` — async function that:
     - Calls requireAuth.
     - Looks up role via getUserRole.
     - If role not in allowedRoles, returns forbiddenError.
     - Returns { user, role }.
   - These functions return either the success value OR a NextResponse error — the caller checks and returns early if it's an error.

4. Create a sample protected API route at `src/app/api/admin/health/route.ts`:
   - Uses `requireRole(request, ['ADMIN'])`.
   - Returns `{ status: "ok", role: "ADMIN" }`.
   - This is a smoke test for RBAC.

All functions should be fully typed with TypeScript. No `any`. Use the project's Supabase types.

PROMPT 20: Adaptive Question Selection Engine
--------------------------------------------------------------------------------

Build the server-side adaptive question selection engine. This runs on the server — the client never sees the question pool or difficulty logic.

1. Create `src/features/runner/lib/adaptive.ts` — Adaptive Engine Logic:
   - Function `computeTargetDifficulty(responses: Response[])` → number (1–4):
     - Input: array of responses for current section, ordered by creation time.
     - Look at the last 2 responses.
     - If both correct → difficulty +1 (max 4).
     - If both incorrect → difficulty -1 (min 1).
     - Otherwise → unchanged.
     - Initial difficulty (no responses yet): 2.
   - Function `selectNextQuestion(params)`:
     - Inputs: testId, sectionName, answeredQuestionIds, targetDifficulty.
     - Query `test_questions` WHERE test_id AND section_name AND base_difficulty = targetDifficulty AND question_id NOT IN answeredQuestionIds.
     - Random selection from matching pool.
     - If no match at targetDifficulty, try fallback (documented below).
     - Return the question (without correct_answer or explanation fields — NEVER send these to client).
   - Function `fallbackSelection(params)`:
     - Try difficulty ± 1 from target, then ± 2.
     - If all exhausted, return null (section complete).
     - Log the fallback event: { attemptId, section, target, actual, reason }.

2. Create API route `src/app/api/student/next-question/route.ts`:
   - Input: { attemptId, sectionName }.
   - Auth: verify current user owns the attempt (via student_profiles.auth_user_id).
   - Logic:
     a. Get attempt (verify status = IN_PROGRESS).
     b. Get all responses for this attempt + section.
     c. Check if section is complete (responses count >= section's question_count). If yes, return { sectionComplete: true }.
     d. Compute target difficulty.
     e. Select next question using adaptive engine.
     f. Return question object (id, stem, passage, image_url, options, type) — NO correct_answer, NO explanation.
     g. Also return: { questionNumber, totalInSection, sectionName, difficultyServed }.

3. Update the test runner (`src/app/student/test/[assignmentId]/page.tsx`):
   - Replace any "load all questions at once" pattern with sequential fetching via `next-question` API.
   - When entering a section, call next-question. On answer + next, save response then call next-question again.
   - Handle section transitions: when sectionComplete is returned, show "Section Complete! Moving to {nextSection}..." message for 2 seconds, then load first question of next section.
   - When all sections complete, navigate to review screen.

4. Write unit tests in `tests/unit/adaptive.test.ts`:
   - Test computeTargetDifficulty with various response histories.
   - Test 2-correct raises difficulty.
   - Test 2-incorrect lowers difficulty.
   - Test mixed responses keep difficulty unchanged.
   - Test boundaries (doesn't exceed 4, doesn't go below 1).
   - Test initial state returns 2.

PROMPT 21: Score Computation
--------------------------------------------------------------------------------

Build the scoring system. All scores are out of 100, no negative marking.

1. Create `src/features/reporting/lib/scoring.ts`:
   - Function `computeSectionScore(responses: Response[])` → number (0–100):
     - Count correct (is_correct = true) vs total responses in section.
     - Score = (correct / total) × 100. Round to 2 decimal places.
     - No negative marking: unanswered / incorrect = 0 points.
   - Function `computeOverallScore(sectionScores: Record<string, number>, sectionWeights: Record<string, number>)` → number:
     - Weighted average where weights are the question counts per section.
     - Formula: sum(score_i × weight_i) / sum(weight_i).
   - Function `computeAttemptScores(attemptId)`:
     - Fetch all responses for the attempt.
     - Group by section_name.
     - For each section, compute section score.
     - Compute overall weighted score.
     - Compute raw_accuracy (total correct / total questions × 100).
     - Compute time_spent_seconds.
     - Return { scoreOutOf100, sectionScores, rawAccuracy, timeSpentSeconds }.

2. Update the submit API route (`src/app/api/student/submit/route.ts`):
   - After marking MCQ answers as correct/incorrect, call computeAttemptScores.
   - Update the attempt row:
     - `score_out_of100` = overall score.
     - `section_scores` = JSON object { "Numeracy": 85.0, "Reading": 72.5, ... }.
     - `raw_accuracy` = raw accuracy.
     - `time_spent_seconds` = total time.
   - Set status to COMPLETE (or WRITING_PENDING if writing exists).

3. Write unit tests for scoring functions:
   - All correct → 100.
   - All incorrect → 0.
   - Mixed → correct percentage.
   - Weighted average with different section sizes.
   - Empty section → 0.
