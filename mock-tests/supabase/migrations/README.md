### Why config and cron are exported separately

A schema dump reproduces structure, never data. But `coverage_thresholds`,
`item_thresholds`, `dim_year_level_cap`, `platform_capacity`, `refresh_blackout`
and `product_tax_treatment` are **configuration whose absence silently disables
features** rather than raising an error — a NULL `min_items_per_subtopic` is
exactly the defect migration 042 was written to catch. And `pg_cron` schedules are
rows in the `cron` schema, so no DDL dump ever reproduces them.

Since **086** the config list is *discovered*, not enumerated. Any reporting table
named `*_thresholds`, or enforcing a single row with `CHECK (id = 1)`, is exported
automatically; only the four tables that follow neither convention are still listed
by hand. Before that, adding `item_thresholds` in 077 silently left it out of the
baseline — a restore would have rebuilt the table on DEFAULT values, quietly
reverting every item flag band. That was the third time a hand-maintained list in
this export missed a new object (after 058/066/071), so the mechanism was fixed
rather than the entry added.

ETL-populated tables (`dim_student`, `dim_item`, `dim_skill_area`, `dim_date`, the
facts) are deliberately **not** exported: they are rebuilt by the load functions,
and dumping them would bake today's data into a schema baseline.

## How the export reaches the database

There is no `pg_dump`, `psql`, Supabase CLI or connection string in this
environment — only the project URL and API keys. The export therefore runs through
three **bounded, read-only** functions (migrations 051/052) behind one
service-role-only public entry point (053):

- They accept only a whitelisted part name and **execute no caller-supplied SQL**.
- They return catalog-derived DDL text only.
- `EXECUTE` is granted to `service_role` alone, revoked from `PUBLIC`, `anon`,
  `authenticated`, and the entry point also checks `current_user` explicitly.

This is deliberately **not** a general `exec_sql(text)` function. That would be an
arbitrary-SQL surface over HTTP and a SQL-injection foothold — a critical
vulnerability introduced to solve a tooling problem. The A15 `anon_executable_rpc`
check covers these functions like every other public wrapper.

> ## ⚠️ Do not run `CREATE EXTENSION pgtap` without `WITH SCHEMA extensions`
>
> pgtap defines `has_role(name) → text`. This app defines
> `has_role(user_role) → boolean`, used by every RLS policy. Installed into
> `public`, pgtap's signature wins overload resolution for `has_role('ADMIN')`,
> the policy expression evaluates to **text**, and Postgres raises
> `42804: argument of OR must be type boolean, not type text`.
>
> **This was observed live** — installing the test framework broke the access
> model it was meant to verify. Migration `050` moves pgtap to `extensions` and
> adds a guard that raises if it ever lands in `public` again.
>
> Test scripts must schema-qualify pgtap calls (`extensions.is(...)`) and set
> `search_path = public, extensions` — public first. `supabase/tests/assurance.sql`
> does both.

## Why this is dangerous

`supabase db reset` rebuilds a database **from the files in this folder**. Run it
against a local instance and you get `001`–`016` only — every reporting object
disappears: the `reporting` schema's dimensions, facts, materialised views, the
`reporting_ro` role and its grants, all `public.*` SECURITY DEFINER wrappers,
and every `pg_cron` schedule. The application would then fail at runtime against
functions that no longer exist, and would do so in ways that look like
authorisation bugs rather than missing schema.

**Do not run `supabase db reset` until this folder has been re-baselined.**

## Why 017–027 cannot simply be written out now

`supabase_migrations` stores the version and the name — not the SQL. The text of
`017`–`027` was never committed anywhere, so it cannot be recovered verbatim.
`028`–`039` are recoverable from the session that created them, but writing out
only those would produce a folder that *looks* almost complete while silently
missing eleven migrations, which is worse than one that is obviously stale.

## Recovery path

Re-baseline from the live database rather than trying to reconstruct history:

```bash
# Schema only, no data, no ownership/acl noise that will not apply locally.
pg_dump "$SUPABASE_DB_URL" \
  --schema-only --no-owner --no-privileges \
  --schema=public --schema=reporting \
  -f supabase/migrations/040_baseline_schema.sql
```

Then, separately, capture what `pg_dump` does not reproduce:

- **`pg_cron` schedules** — `SELECT jobname, schedule, command FROM cron.job;`
  There are fourteen `rpt-*` jobs; they are data in the `cron` schema, not DDL.
- **Role grants** — `reporting_ro` membership and the `REVOKE ... FROM PUBLIC` /
  `GRANT EXECUTE ... TO authenticated` pairs on every `public.*` wrapper.
  `--no-privileges` deliberately drops these, and without them the SECURITY
  DEFINER functions are either uncallable or over-exposed.
- **Seed/config rows** — `reporting.coverage_thresholds`,
  `reporting.funnel_thresholds`, `reporting.dim_year_level_cap`,
  `reporting.platform_capacity` (the A-13 concurrency assumption),
  `reporting.refresh_blackout`.

## Going forward

Write the `.sql` file **and** apply it, or apply it and immediately export the
